## 2. 功能详解

- **`EnsureValid` 与 `Refresh` 的语义故意分开**（`backend/internal/tokenmgr/tokenmgr.go`）：`EnsureValid` 才做"缓存没过期就不调钉钉"的单飞（single-flight）优化，`Refresh` 永远无条件真的调一次。**这是实现中真实纠正过的一个 bug**：第一版把"拿到锁后重新检查缓存"这一步也塞进了 `Refresh`，导致管理员点 `POST /admin/token/refresh` 时如果缓存恰好没过期，实际上什么都没做——"强制刷新"变成了"有时候刷新"。
- **发送失败与 `getbymobile` 失败是两条不同的清缓存路径**：`resolveUserID` 命中缓存后不会再调 `getbymobile`，所以"用户不在企业内"这类错误更可能发生在 `asyncsend_v2` 那一步（拿着一个已经失效的缓存 userid 去发）——设计计划 §2 描述的过期策略本意就是"发送失败且错误码是用户不存在时删掉这一行"，不是解析阶段。
- **`asyncsend_v2` 成功只代表"受理"，不代表送达**：拿到 `task_id` 后记 `ACCEPTED` 并发对应结果事件，随后在**独立 goroutine**里延迟几秒退避回查 `getsendresult`（不引入定时任务框架），查到已完成才记 `CONFIRMED`。⚠️ **回查不能在消费事件的同一个事务里做**——那会一直占着数据库连接和这条消息的 inbox 声明，`time.Sleep` 几秒会拖住整个消费循环的吞吐；`confirmLater` 用调用方传入的长生命周期 `ctx`（组件关闭时取消，goroutine 跟着退出，不会泄漏）。
- **`integration.im.result.v1` 的 `Event.Version = attempt*10 + phase_ordinal`**（`phase_ordinal`：ACCEPTED=1，CONFIRMED=2）：同一个 `record_id` 在这条 subject 上的所有结果事件（跨阶段、跨重试）必须严格递增，否则 `infra-notification` 的 `event_inbox` 会把后到的事件当重复消息吞掉——同 `infra-notification` consumer.go 那次 `dispatch.im.v1` version 单调 bug 是同一类教训，`attempt` 原样透传自触发这次投递的 dispatch payload。
- **`command_idempotency` 表从一开始就没建**（`migrations/002` 顶部注释）：全项目核对后确认这张表只用于外部调用方提供 `idempotency_key` 的写命令 RPC，本组件没有任何写 RPC（`BatchGetDeliveryStatus`/`GetChannelHealth` 都是读），事件消费幂等完全由 `event_inbox` 负责。
- **`ClassifyError` 按 errmsg 关键词匹配，不是 errcode 数字**（`backend/internal/dingtalk/classify.go`）：没有真实钉钉沙盒可验证具体错误码是否真的对应"用户不存在"/"限流"这些场景，这是"只做到能编译通过的程度"这条既定决策（03-阶段三 Task 9）的直接后果。区分不了的错误一律当可重试。

## 3. 完整契约清单

**gRPC `integration.im.v1.ImChannelService`**（族级契约，五个成员共用同一份 proto）：

| rpc | 类型 | 说明 |
|---|---|---|
| `BatchGetDeliveryStatus` | 读 | 防 N+1，排障用 |
| `GetChannelHealth` | 读 | 给运维看，不给业务判断用 |

**REST**（`/integration/im/**`，族级前缀）：

| 路径 | 权限键 | 说明 |
|---|---|---|
| `GET /admin/deliveries` | `integration.im.admin` | 排障 |
| `POST /admin/token/refresh` | `integration.im.admin` | 应急强制刷新 |

**发布事件：** `integration.im.result.v1`（核心，族级 subject，`adapter=dingtalk`）。
**消费事件：** `infra.notification.dispatch.im.v1`（族级，先判 `target_adapters` 再处理）。

详细字段与判据见 `docs/design/integration-im-dingtalk.md`。

## 4. 数据模型

| 表 | 分区 | 说明 |
|---|---|---|
| `dingtalk_user_map` | 不分区 | 手机号→userid 缓存，只在组件内部使用，不进任何事件 |
| `dingtalk_token` | 不分区 | 单行（`id=1` CHECK 约束） |
| `delivery_attempts` | 月（归档窗口 1 个月，全系统最短） | 写入即终态，`(record_id, attempted_at DESC)` 索引取最新状态 |
| `event_outbox`/`event_inbox` | 周 | 标准两张 |

**实测验证**（真实 Postgres + 真实 NATS + `httptest` 模拟钉钉，非 mock 钉钉之外的任何一层）：token 缓存的"未过期不重复调"与"强制刷新一定真的调"两条语义分开验证、手机号缓存写入/覆盖/删除、`delivery_attempts` 按 phase 优先级取最新状态、`target_adapters` 自过滤、完整 ACCEPTED→延迟回查→CONFIRMED 链路（含退避轮次）、结果事件 version 序列 `[11, 12]`、用户不在企业内时不可重试且清缓存、迁移连跑两次幂等、Docker 镜像自检。

```bash
export TEST_PG_DSN="postgres://postgres:<密码>@localhost:5432/brickkit_test_db?sslmode=disable"
export TEST_NATS_URL="nats://localhost:4222"
```

跑测试前先把 schema 建出来：

```bash

go run ./backend/cmd/migrate up
```

`backend/internal/dingtalk` 的测试全部用 `httptest.Server` 模拟钉钉的四个接口，不需要任何真实凭据；`consumer_test.go` 同样用 `httptest` 起一个假钉钉服务器 + 真实 Postgres/NATS，验证的是"消费到派发事件之后内部编排对不对"，不是"钉钉真的这样回"——那部分需要真实测试企业才能验证，本阶段按既定决策跳过。

## 6. 排障

| 症状 | 根因 | 修法 |
|---|---|---|
| 装了三个 IM 通道，一条通知收到三遍 | 消费 `dispatch.im.v1` 时漏了 `target_adapters` 自过滤这一步 | 检查 `dispatchHandler` 里 `containsAdapter` 的调用有没有被绕过 |
| `POST /admin/token/refresh` 点了但 token 没变 | tokenmgr 的 `Refresh` 混进了"缓存没过期就跳过"的判断（这是本组件出现过的真实 bug） | 确认 `Refresh` 直接调 `doRefresh`，不做任何缓存有效性检查；只有 `EnsureValid` 才做 |
| `delivery_attempts` 一直停在 `ACCEPTED` | 延迟回查 goroutine 可能因为组件重启而中断（`confirmLater` 跟着 `ctx` 取消退出，不会持久化"还有一条没查完"） | 目前没有持久化的补偿机制——这是已知缺口，`infra-notification` 那边设计了"停在 ACCEPTED 超过阈值要能被查出来"的排障视图，本组件重启期间正在回查的记录会永久停在 ACCEPTED，等真实使用中发现是真问题再补重启后扫描未完成任务的逻辑 |
| 结果事件被 `infra-notification` 那边的 `event_inbox` 吞掉 | `Event.Version` 没有按 `attempt*10+phase_ordinal` 算，或者 `attempt` 没有从 dispatch payload 原样透传 | 检查 `publishResultTx` 的调用参数 |
| 单元测试里 `ClassifyError` 判断的错误码分类不对 | 分类按 errmsg 关键词匹配，不是真实钉钉错误码——本阶段没有真实沙盒验证过 | 等有真实测试企业凭据，用真实响应核对 `classify.go` 的关键词列表 |
