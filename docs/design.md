# integration/im-dingtalk 的设计

本页写这个组件为什么这样设计：术语、拥有的数据、规则、命令与事件、依赖、实现状态与未决问题。写给要修改它的人与 AI。怎样使用、部署与配置在 `BRICKKIT.md`；代码在哪、怎样构建与测试在 `AGENTS.md`。

跨组件的规则在装配项目：
- 协议 10：对外命令、入站回调、凭据与出站网络、通知的路由与交互按钮；
- 决定 D68：渠道不调用业务组件、不记录决定，只经事件读员工。

本组件与通知组件、与任务所属组件之间的约定在线协议第 20 章（渠道成员与交互动作）。对外命令的状态在线协议第 13 章（SDK 的 `extcmd`）。

首批范围是装配项目阶段计划 C10 的 P0 定的，设计考试之后改过（AI 定，待复核；`dev/rebuild/c10-data/exam-p1/`）。

## 边界

钉钉渠道做三件事：
- 把通知组件交来的投递发到钉钉（互动卡片）；
- 接收钉钉的回调，把“谁点了哪个按钮”作为动作事件发到自己的流上；
- 让用户本人把自己的钉钉账号绑定到平台账号。

| 不在这里 | 归谁 |
| --- | --- |
| 该通知谁、投哪些渠道、偏好 | `infra/notification` |
| 审批的决定、动作授权的签发与核对 | 任务所属组件（流程内核，线协议 P17.19、P20.7） |
| 员工、账号与岗位 | `mdm/employee`、身份成员 |

## 术语

| 业务叫法 | 定义 | 代码标识符 |
| --- | --- | --- |
| 渠道账号绑定 | 一个平台主体与一个钉钉用户（`userId`）的对应，由用户本人经钉钉授权建立 | `binding` |
| 绑定会话 | 一次绑定：发起的主体、随机的 `state`（只存摘要）、到期 | `bind_session` |
| 投递 | 通知组件交来的一次：投递身份、发送方与意图、收件主体、类别、标题、链接、可选的动作；在本组件是一条对外命令 | `delivery` |
| 动作授权 | 所属组件签发的、不是秘密的身份，绑定任务、主体、版本与允许的动作（线协议 P20.5） | `grant` |
| 按钮随机值 | 本组件为每个投递的每个动作生成的一次性随机值，放在卡片按钮里；只存摘要 | `nonce` |
| 对外命令 | 发给钉钉的一次“发送互动卡片”（线协议第 13 章） | SDK 的 `extcmd` 表 |
| 回调 | 钉钉推到本组件的事件（按钮点击）：签名、加密的报文 | `callback` |
| 隔离区 | 验过签、但处理不了的回调：留着给人看，并告警 | `callback` 的 `quarantined` |
| 动作事件 | 本组件在自己的流上发的“某主体对某授权执行了某动作”（线协议 P20.6） | `integration.im_dingtalk_action.recorded.v1` |

## 拥有的数据

右列的期限是本组件的技术期限，不是法定保留；每天的清理作业（`purge`，3.0.3 起）按它删除，停在 `received` 的回调在处理之前不删。

| 表 | 内容 | 终态与保留 |
| --- | --- | --- |
| `binding` | 主体、钉钉用户、状态（`active`、`ended`）、建立与结束的时刻、结束的人；主体与钉钉用户各自在 `active` 里唯一 | `ended` 的保留 400 天（回调里的旧用户能查到曾是谁） |
| `bind_session` | `state` 的摘要、主体、到期（10 分钟）、用过的时刻 | 过期 1 天后删 |
| `delivery` | 调用方、投递身份（“调用方 + 投递身份”唯一）、请求的摘要（幂等比较）、发送方与意图身份、合并键与序号、收件主体、钉钉用户、类别、标题、链接、到期、动作（授权身份、动作、显示名、按钮随机值的**摘要**）、对外命令的身份、结果 | 保留到到期之后 7 天，至少 90 天 |
| SDK 的 `extcmd` 表 | 对外命令与它的尝试；参数里没有随机值原文（发送时现生成，见 ID03） | 随 SDK |
| `callback` | 钉钉的事件身份（唯一）、收到的时刻、密文的摘要与签名参数（纠纷时能证明收到过什么）、解密后的正文（随机值替换为摘要）、状态（`received`、`published`、`quarantined`、`ignored`）、原因 | 保留 180 天（纠纷周期，协议 10） |

## 规则

| 规则 | 内容 |
| --- | --- |
| ID01 | **投递**（线协议 P20.1）：系统面 `be.channel.v1.ChannelService.Deliver`，操作 `integration.im_dingtalk.system.deliver`（授予通知组件）。在一个事务里：按“调用方 + 投递身份”找已有的投递，请求摘要相同答第一次的结果，不同答 `IDEMPOTENCY_KEY_REUSED`；类别、标题、链接、到期按线协议 P18.3、P18.5 核对，不合的答 `REQUEST_INVALID`；收件主体没有 `active` 的绑定答 `unmapped`、什么也不写；否则写投递（每个动作生成按钮随机值、只存摘要）与一条对外命令（`extcmd`，业务参考号是投递身份，操作 `send_card`，本地放弃时刻是投递的到期，线协议 P13.14），答 `accepted` |
| ID02 | **卡片**：标题是投递的标题，按纯文本放入（标题来自单据，可能含用户输入：卡片 Markdown 会解释的字符都加反斜杠转义，换行与控制字符换成空格；钉钉的模板字段实际按 Markdown 还是纯文本渲染，接真实钉钉前核对，未决问题）；正文是类别的显示名，同样转义；按钮是动作（每个动作一个回调按钮，值里带投递身份、动作与按钮随机值）与一个“在系统中处理”（跳转按钮，地址是部署配置的前端地址 `DINGTALK_LINK_BASE` 加投递的链接）；没有动作的只有跳转按钮 |
| ID03 | **发送**（线协议第 13 章、P20.2）：`extcmd` 的工作项认领命令，取（缓存的）访问令牌，调用钉钉“发送互动卡片”，`outTrackId` 是投递身份。按钮随机值在发送时生成，只存它的摘要：每次发送重新生成，摘要换掉旧的，所以原文从不落库。结果分类：钉钉受理（新接口答 `success` 为真）→ `succeeded`，结果只到“已发送”（钉钉不回执送达）；答了却不受理（`success` 为假）→ `rejected`；连接失败、限流（HTTP 429）、令牌被拒（401、403，清掉缓存）→ “肯定没处理”，退避后重发；读取超时、5xx → “结果未知”；其余 4xx → `rejected`。能力声明写“不去重、不可查询”（同一个 `outTrackId` 再发，钉钉是否当作重复，没有核实过），所以结果未知的命令不重发，到放弃时刻转 `failed`（`expired`），不进人工：重复的通知与漏一条通知都不是业务后果，宁可少发也不重复发。凭据错误、用户不存在是明确拒绝 → `rejected`。投递到期仍没发出的 → `failed`（`expired`） |
| ID04 | **结果事实**（线协议 P20.2）：命令终结时在同一事务里发 `integration.im_dingtalk_delivery.recorded.v1`：投递身份、调用方、发送方与意图身份、收件主体、结果（`sent`、`failed`、`rejected`、`expired`）；不带标题与链接 |
| ID05 | **访问令牌**：按应用的 `DINGTALK_APP_KEY`、`DINGTALK_APP_SECRET` 向新接口 `POST /v1.0/oauth2/accessToken` 取（密钥在请求体里，从不进地址；取不到时的错误不带传输的细节），缓存到它的有效期前 5 分钟；钉钉答令牌失效时清掉缓存：发卡片本次按“肯定没处理”退避、下一次重取；换取用户（旧接口答 40014、42001）当场重取、再试一次 |
| ID06 | **回调的接收**（协议 10 的入站回调、线协议 P20.6）：<br>- 入口：公开路由 `POST /api/im-dingtalk/callback`，不要用户身份；组件限大小 64 KiB；限速在部署的边缘做（组件里不做，格里没有配置，未决问题）。<br>- 验签：按钉钉的事件订阅方案。查询参数的时间戳要在 5 分钟之内；签名是 `token`、时间戳、随机串与密文排序后拼接的 SHA-1，常数时间比较。不对的丢弃并计数，不写库。<br>- 解密：用 `DINGTALK_CALLBACK_AES_KEY` 解开（AES-256-CBC），明文里的应用标识要等于 `DINGTALK_APP_KEY`。<br>- 去重：按事件身份去重，已见过的直接答成功。<br>- 存下：在一个事务里存 `received`（随机值替换为摘要，另存密文的摘要与签名参数），同时登记处理的工作项。<br>- 答复：**提交之后**答加密的 `success`。存不下（数据库不可用）时答失败，让钉钉重推 |
| ID07 | **回调的处理**（工作项，以回调行幂等）：<br>- 不是卡片回调的事件：`ignored`。<br>- 按 `outTrackId` 找投递，找不到：隔离。<br>- 按钉钉用户找 `active` 的绑定，没有：隔离。<br>- 绑定的主体要等于投递的收件主体，不等：隔离（卡片被转发给了别人）。<br>- 动作要在投递的动作里，随机值的摘要要等于投递记下的这个动作的摘要，不等：隔离。<br>- 都过了，发动作事件（ID08），回调 `published`。<br>- 停在 `received` 超过 5 分钟的，告警 |
| ID08 | **动作事件**（线协议 P20.6）：在本组件的流 `integration.im_dingtalk` 上发 `integration.im_dingtalk_action.recorded.v1`（`schemas/channel/action.v1`），字段如下，经发件表，与回调的状态同一个事务：<br>- 动作身份（UUIDv7）；<br>- 渠道成员 `integration/im-dingtalk`；<br>- 受众（投递的发送方）；<br>- 主体；<br>- 动作授权的身份；<br>- 动作；<br>- 点击的时刻。<br>本组件不调用所属组件、不记录决定；所属组件核对后执行（P20.7、P20.8），被拒时它自己给用户发站内意图 |
| ID09 | **隔离区**：<br>- 用户面 `GET /api/im-dingtalk/callbacks?state=quarantined`（操作 `integration.im_dingtalk.callback.read`），列出原因与时刻；正文里没有随机值。<br>- 进隔离区写一条告警级日志（`event=dingtalk_callback_quarantined`）。<br>- 不自动重放 |
| ID10 | **本人绑定**（线协议 P20.9）：<br>- 发起：用户面 `POST /api/im-dingtalk/bindings/start`（操作 `integration.im_dingtalk.my_binding.manage`，给所有用户），答钉钉授权页的地址：带 `state`（随机值，只存摘要，10 分钟）与回跳地址 `DINGTALK_OAUTH_REDIRECT`。<br>- 回跳：`GET /api/im-dingtalk/bindings/callback?code=…&state=…`，**要登录**（同一个操作，浏览器经边缘带着会话）：只有发起这次绑定的主体能完成它，别人把自己发起的授权链接发给受害人、受害人同意，也绑不上（P20.9）。核对 `state`（存在、未过期、未用、发起主体是当前登录的主体，原子作废），用 `code` 向钉钉换取用户身份，得到钉钉用户后为 `state` 的发起主体建立绑定，然后跳回前端。这个主体已有绑定的，旧的结束（结束也写审计）；这个钉钉用户已绑定给别人的，拒绝。<br>- 本人查看与解除：`GET /api/im-dingtalk/bindings/me`、`DELETE …/me`（同一个操作）。<br>- 管理员：`GET /api/im-dingtalk/bindings`（`integration.im_dingtalk.binding.read`，游标分页）；`DELETE /api/im-dingtalk/bindings/{principal}`（`integration.im_dingtalk.binding.end`），只能结束、不能设置。<br>- 每次建立与结束都写审计（审计的变更里写 `binding`：`bound` 或 `ended`） |
| ID11 | **能力声明**（协议 10）：<br>- 按业务参考号去重：否；<br>- 查询：否；<br>- 请求的过期时刻：否；<br>- 签名回调：是（回调只有按钮点击，没有命令的终态）；<br>- 不可撤回的命令：无（重复或漏掉的通知不是业务后果） |
| ID12 | **凭据**：<br>- 应用密钥、回调的 `token` 与 AES 密钥都是密钥引用，不写日志；应用密钥只在请求体里发给钉钉，旧接口的地址里只带短期的访问令牌（SDK 的出站调用不把地址的查询串放进错误）。<br>- 按钮随机值与 `state` 只出现在发给钉钉的消息与用户的浏览器里。<br>- 回调密钥轮换时新旧同时有效，以后做；首批一个 |

## 部署与替换

- **负载与放置**：低负载。但本组件不和不受信任的成员放进同一个外壳：同一个外壳里的成员共用总线连接，能在本组件的流上发布动作事件（线协议第 20 章的信任前提）。放 `be/go-infra`（同外壳的是基础成员；验收格里另有套件的探针 `test/probe-go*`，它们只在自己的流上发布，客户的部署不带探针）或单跑。
- **对外入口**：回调与绑定的回跳要经边缘暴露到钉钉与用户浏览器能到达的地址，与用户接口分开路由。部署不能从外网到达时，按钮与绑定都不起作用（链接照常），本组件仍能发卡片。
- **替换**：同契约（`be.channel.v1`）的渠道成员可以多选并存。

## 验证故事

1. 用户本人绑定钉钉后，审批待办投到钉钉：卡片上有“同意”与“在系统中处理”；在钉钉点“同意”，所属组件核对授权后批准，任务离开待办。
2. 同一个按钮再点一次（或钉钉重推回调）：所属组件答第一次的结果，不产生第二个决定；任务版本已变（被别人处理、被撤回）时被拒，用户收到一条站内消息说明没执行。
3. 伪造的回调（签名不对、时间戳过旧）被丢弃，不写库；签名对、但钉钉用户没有绑定，或卡片被转发给别人点的，进隔离区。
4. 收件人没有绑定钉钉：答 `unmapped`，通知组件只写站内消息。
5. 钉钉暂时不可达：命令退避后重发；读取超时的命令不重发，到期记 `expired`。
6. 管理员结束一个绑定：之后发给这个主体的投递答 `unmapped`；管理员不能把别人的平台账号绑定到某个钉钉用户。

## 未决问题

- **钉钉接口的细节尚未核实**：发送互动卡片、回调的签名与加密、OAuth 换取用户身份、错误码，都是按公开文档建模（截至 2026-11），模拟器照同一套实现。接真实钉钉前，用它的测试企业复核，不一致的地方改适配器。另外两点也待核实：
  - 互动卡片的回调要不要另行注册、签名是否同上；
  - 同一 `outTrackId` 重复投放是否报“已存在”：如果是，可以当作去重来用，读取超时就能安全重发。
- **Stream 模式**：钉钉推荐的 Stream 模式（出站长连接）不需要公开入口，以后作为另一种接收方式（线协议第 20 章的“不在本版”）。
- **卡片的更新与撤回**：线协议第 20 章的“不在本版”。
- **多应用与回调密钥的轮换**：首批一个应用。
